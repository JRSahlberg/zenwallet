## Context

ZenWallet is a fresh Vite + React 19 + TypeScript app (`src/App.tsx` is still the starter counter). Every later feature — UI shell, persistence, import/export, charts — will sit on top of some notion of "a wallet with accounts and transactions." If we let those concepts emerge ad-hoc inside components, each screen will redefine slightly different shapes, money math will drift, and we'll end up refactoring before we've shipped anything.

This design locks the core domain before the UI lands: a pure TypeScript module that owns the types, the arithmetic, and the invariants, with a reducer as the single mutation surface. Constraints from `CLAUDE.md` apply: strict TS config (`erasableSyntaxOnly`, `verbatimModuleSyntax`, `noUnusedLocals/Parameters`), flat ESLint without type-aware rules, React Compiler disabled, and no test runner yet.

## Goals / Non-Goals

**Goals:**
- Establish the canonical domain vocabulary: `Wallet`, `Account`, `Transaction`, `Money`, `Currency`, `AccountId`, `TransactionId`, `WalletId`.
- Represent money exactly (no floats) using `bigint` minor units tagged with an ISO-4217 currency code.
- Provide a pure reducer `(state, action) => state` covering create-wallet, add-account, rename-account, archive-account, post-transaction, void-transaction.
- Provide a handful of pure selectors (balance-of-account, transactions-for-account, wallet-totals-by-currency) so UI layers don't re-derive the same things.
- Enforce invariants at the reducer boundary: no negative-id, no duplicate ids, currency consistency per account, no posting to archived accounts, no voiding a void.
- Keep it importable as a single barrel (`src/domain/index.ts`) so consumers write `import { walletReducer, type Wallet } from "@/domain"` (or relative equivalent).

**Non-Goals:**
- No UI, routing, or styling changes. `App.tsx` stays as-is.
- No persistence layer, no storage adapter, no serialization contract beyond the types being JSON-shaped. Persistence is a future change.
- No multi-wallet sync, no multi-user, no auth. State is single-wallet, single-process, in-memory.
- No test runner — `CLAUDE.md` says none is configured, and introducing one is a separate change. Correctness is enforced by types + hand-run `tsc -b`.
- No budgeting, categories, recurring transactions, attachments, tags, or reporting. Those are follow-up capabilities that depend on this one.
- No React Compiler usage; domain is React-free anyway.

## Decisions

### 1. Money as `{ amount: bigint; currency: Currency }` in minor units
Store amounts as `bigint` in the currency's minor unit (cents, pence, öre), not as `number`. Floats lose precision on sums of large transaction histories; `Number` can't safely represent `> 2^53 - 1` minor units. `bigint` sums are exact and cheap.
- **Alternative considered:** `number` + "just round at the edges." Rejected — rounding bugs are exactly the class of bug we can't afford in a wallet.
- **Alternative considered:** `decimal.js` / `big.js`. Rejected — adds a dependency and JSON serialization ceremony for something `bigint` already gives us natively. We'll revisit if/when we need non-integer minor units (we don't).
- **Consequence:** JSON serialization of `bigint` is non-trivial. We'll defer it: persistence is a future change and will own the serializer. Within this change, state stays in-memory.

### 2. IDs are branded string types, generated by the caller
Define `type WalletId = string & { readonly __brand: "WalletId" }` (same for `AccountId`, `TransactionId`). The reducer accepts pre-generated IDs on action payloads rather than generating them internally.
- **Why:** Pure reducers must be deterministic; generating IDs internally would require passing a clock/rng, which leaks I/O into the domain. Callers (UI or test harness) own ID generation.
- **Alternative considered:** numeric auto-increment IDs managed by the reducer. Rejected — breaks determinism and makes merging state across sessions (future persistence) harder.
- **Consequence:** we need a tiny `newId()` helper somewhere for convenience. It lives outside the reducer (e.g. `src/domain/ids.ts`) and is explicitly impure.

### 3. Transactions are append-only; "delete" is "void"
A posted transaction is never removed from the account's transaction list. "Voiding" flips a `voided: boolean` flag and excludes the row from balance calculations.
- **Why:** audit trail and undoable UX. Hard-deletes make reconciliation impossible once we add import/export.
- **Alternative considered:** hard delete with a separate audit log. Rejected — two sources of truth, easy to desync.
- **Consequence:** balance selectors must filter `voided === false`. Documented in the spec.

### 4. Balance is derived, never stored
`balanceOfAccount(state, accountId)` folds over non-voided transactions. We do not cache balances on the `Account` record.
- **Why:** caches drift. The total transaction volume per account is small enough (human-scale) that O(n) per read is fine.
- **Alternative considered:** maintain a running balance on `Account` updated by the reducer. Rejected for now — premature optimization and an extra invariant to maintain. Revisit only if a profiler flags it.

### 5. Currency is fixed per account, not per transaction
Each account declares its currency on creation. Transactions on that account inherit the account's currency and cannot override it.
- **Why:** mixed-currency accounts force every read to ask "convert to what?" — a can of worms we don't need yet. Cross-currency transfers become "two transactions in two accounts" and that's a later feature.
- **Alternative considered:** per-transaction currency with on-the-fly FX. Rejected — FX rates are I/O, and this change is pure.

### 6. Reducer shape: discriminated-union actions, plain old data state
```
type Action =
  | { type: "wallet/create"; id: WalletId; name: string }
  | { type: "account/add"; accountId: AccountId; name: string; currency: Currency; openingBalance: Money }
  | { type: "account/rename"; accountId: AccountId; name: string }
  | { type: "account/archive"; accountId: AccountId }
  | { type: "transaction/post"; accountId: AccountId; transactionId: TransactionId; amount: Money; occurredAt: string; memo?: string }
  | { type: "transaction/void"; transactionId: TransactionId }
```
State is a single `Wallet` object (or `null` before `wallet/create`). No Redux-style slices — we have one aggregate.
- **Why:** matches React's `useReducer` shape exactly, so when the UI lands it drops in without an adapter. Discriminated unions give us exhaustiveness checking for free.
- **Alternative considered:** class-based `Wallet` with methods. Rejected — fights `verbatimModuleSyntax` and immutability, and React state wants plain data anyway.

### 7. Invariant violations throw, not return `Result`
Illegal actions (post to archived account, currency mismatch, duplicate id, void-a-void) throw a typed `DomainError`. The reducer does not return a `Result<State, Error>`.
- **Why:** these are programmer errors, not user-input errors. The UI layer validates user input before dispatching; anything that reaches the reducer and violates an invariant is a bug. Throwing surfaces it loudly in dev.
- **Alternative considered:** `Result`-style returns. Rejected — every call site would need to handle both branches, and for programmer errors that's noise. User-input validation is a different layer and belongs in the UI.

### 8. File layout under `src/domain/`
```
src/domain/
  index.ts            // barrel: re-exports types + reducer + selectors
  money.ts            // Money, Currency, addMoney, negateMoney, sameCurrency
  ids.ts              // branded id types + newId() helper
  types.ts            // Wallet, Account, Transaction shapes
  reducer.ts          // walletReducer, Action union, DomainError
  selectors.ts        // balanceOfAccount, transactionsForAccount, walletTotals
  errors.ts           // DomainError class + codes
```
One file per concern, small enough that each is readable top-to-bottom. Barrel re-exports keep import sites clean.

## Risks / Trade-offs

- **Risk:** `bigint` in React state can surprise devtools and third-party libs (some serializers choke). → Mitigation: domain never leaves this module in a serialized form during this change; persistence change owns the serializer.
- **Risk:** caller-generated IDs mean a bug in the ID helper can produce collisions. → Mitigation: `newId()` uses `crypto.randomUUID()` with a brand cast; collisions are astronomically unlikely and the reducer rejects duplicates loudly.
- **Risk:** no test runner means regressions in reducer logic only surface when the UI exercises them. → Mitigation: keep the domain small and obvious; document every invariant in the spec so a future test runner has scenarios to adopt 1:1. Adding Vitest is explicitly a follow-up change.
- **Trade-off:** derived balances are O(n) per read. For human-scale wallets (<10k tx) this is invisible; if the app ever imports bank statements with 100k+ rows we'll revisit caching.
- **Trade-off:** throwing on invariant violations means a single bad dispatch crashes the reducer. That's desired in dev; in prod we'll want an error boundary at the UI layer, which is a UI-layer concern (not this change).
- **Risk:** branded-id types are erased at runtime, so a plain string can be cast into an `AccountId` by mistake. → Mitigation: only construct IDs via `newId()` (or the reducer's payload handlers); don't expose a public `brand()` function. Code review catches casts.
